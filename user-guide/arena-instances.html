Arena Instances & Automatic Capacity

Prepare individual copies of selected duel arenas in a separate void world, then optionally grow their capacity as players need it.

Opt-in: updating the JAR does not activate this system
Both arenas.instances.enabled and arenas.instances.auto-expand.enabled ship as false, with no selected templates. Existing arenas and whole-world cloning keep their current path while instances are disabled. This guide describes the implementation in this source tree; use a build that includes these settings.

How It Works

  1. Create a normal duel arena with corners, both spawns, a saved schematic, and linked kits. This original arena becomes its template.
  2. Select that original arena by name in arenas.instances.templates.
  3. At startup, ShyamDuels validates the source and prepares separate, spaced-out copies in the owned instance world. It copies spawn positions, center, kit links, build settings, and supported gate data.
  4. A generated copy enters matchmaking only after its paste and required chunk/block checks succeed. Existing queue, direct duel, team, party, and tournament flows claim it through the normal arena manager.
  5. Copies reset and become reusable after matches. Optional auto-expansion requests more copies when the configured ready reserve runs low, within both capacity limits.

Capacity means simultaneous matches, not players. Two ready copies of Grass provide two match slots. A team match still uses one slot.

Once a template pool is successfully prepared, its original and legacy world-clone counterparts are excluded from matchmaking for that template. The original remains the editable source: do not count it as an extra slot. Unselected templates and FFA arenas continue using their existing path. If optional bootstrap fails, the plugin reports the failure and retains the existing arena path rather than treating incomplete copies as ready.

Instances vs. Existing Arena Cloning

SystemWhat it copiesWhen to use it
Manual arenasNothing automatically; each registered region is a slot.Small servers or individually built maps.
arenas.cloningThe configured base arena world into numbered world copies.Existing fixed-capacity deployments. This setting is not replaced or enabled by instances.
arenas.instancesSelected DUEL arena schematics into separate regions of one dedicated void world.Per-template capacity and optional bounded expansion without a full world copy for every extra slot.

The two automatic systems can coexist: successfully managed instance templates are skipped by legacy cloning, while unselected eligible templates can still use it. Do not change arenas.cloning merely because you update the JAR.

Template Requirements

  • A valid original DUEL arena, not an FFA arena, legacy clone, or generated copy.
  • Both corners, valid spawn/center locations inside the selected bounds, linked kits, and a saved schematic whose dimensions match the selected region. Match the kit and arena build modes. Gate regions and eject points must also fit inside the template.
  • Use an arena name such as Grass in templates, not a kit name such as Sword unless that is also the actual arena name. Names are matched case-insensitively.
  • A new, unused destination world name, separate from lobby, base arena, and numbered clone worlds. Let ShyamDuels create it; do not pre-create an empty destination with another world manager.
  • Compatible FastAsyncWorldEdit and enough memory, disk, and CPU for the selected schematics and concurrent resets.

Follow Arena Setup first. After editing the physical source, run /arena saveschem Grass and wait for its save confirmation before refreshing the template.

Shipped Configuration

These settings belong inside the existing arenas: section of plugins/ShyamDuels/config.yml. Merge the subsection; do not add a second top-level arenas: key or replace unrelated settings.

yamlarenas:
  instances:
    enabled: false
    world: ShyamDuelsInstances
    templates: []
    initial-copies: 2
    max-copies-per-template: 8
    max-total-copies: 128
    spacing-blocks: 64
    max-concurrent-preparations: 1
    auto-expand:
      enabled: false
      minimum-ready: 1
    overrides: {}

initial-copies2Startup target per template, subject to caps and existing reservations. Not additional copies on every restart.
max-copies-per-template8Per-template ceiling on generated slot reservations.
max-total-copies128Global ceiling on generated slots, excluding manual arenas and legacy clones. Failed, retired, and otherwise reserved slots still count.
spacing-blocks64Minimum gap between copied regions; placement is chunk-aligned. Requires a restart and must agree with persisted layout.

First Activation: Start Small

  1. Back up the plugin data and relevant worlds with the server stopped. Keep the original arena/schematic files.
  2. Check one template with /arena info Grass and test its current duel/reset behaviour.
  3. Stop the server. Merge the example below into config.yml, replacing Grass with your original arena name. Use a destination name that has never been created.
  4. Start the server normally. Read [ArenaInstances] startup warnings and run /arena instances status Grass. Do not assume a requested copy is ready.
  5. Test a duel, round reset, final return, and any gates or special kit mechanics you use. Increase capacity only after observing preparation times and server load.

This example is an opt-in fixed pool, not the shipped default:

yamlarenas:
  instances:
    enabled: true
    world: ShyamDuelsInstances
    templates:
      - Grass
    initial-copies: 2
    max-copies-per-template: 4
    max-total-copies: 8
    spacing-blocks: 64
    max-concurrent-preparations: 1
    auto-expand:
      enabled: false
      minimum-ready: 1
    overrides: {}

With auto-expansion off, normal demand does not grow this pool. Admins can still request copies with /arena instances prepare Grass 1, within the same caps.

Optional Automatic Expansion

After validating the fixed pool, change auto-expand.enabled to true and reload the main config with /sd reload-config confirm. Keep the rest of your instance section intact.

yaml# Inside arenas.instances:
auto-expand:
  enabled: true
  minimum-ready: 1

For example, if two copies exist and one is busy, the remaining ready copy satisfies a reserve of one. If both are busy, the manager can request a replacement reserve copy, provided neither ceiling is reached. It counts already queued/preparing/resetting supply to avoid requesting duplicate copies for the same shortage.

Expansion is bounded, not instant or unlimited
Preparing a map takes time. Players can still encounter no free arena when all copies are busy, preparation/reset work is pending, validation fails, or caps are reached. This is not an automatic match-waitlist or a guarantee of unlimited capacity.

Expanded copies are reused. The system does not automatically shrink the pool by deleting idle regions.

Per-Template Overrides

Replace overrides: {} with a mapping for selected arena names. These keys deliberately differ from the global max-copies-per-template key:

yaml# Inside arenas.instances; Grass must also be listed in templates:
overrides:
  Grass:
    initial-copies: 2
    max-copies: 6
    minimum-ready: 1

Operator Commands

All commands below use the existing shyamduels.admin permission and work from the server console or an authorised player. Slots are numeric IDs from the instance ledger; use the reported slot ID, not an arena name, for slot and retry.

CommandPurpose
/arena instances status [template]Summary, caps, per-template counts, and any pause reason. The default report shows at most 20 templates; name one to inspect it.
/arena instances slot <slot>Inspect state, generated arena name, generation, physical/submitted work, preparation duration, and last error.
/arena instances prepare <template> [count]Request copies within caps. Count defaults to 1; acceptance is not a ready-state confirmation.
/arena instances retry <slot>Retry an eligible failed slot after resolving its cause. Reuses the reservation rather than allocating another region.
/arena instances refresh <template>Validate the saved template revision and request updates for eligible idle copies. Does not capture unsaved physical changes.
/arena instances resumeAttempt to resume a safely recoverable paused manager. Does not bypass ownership, manifest durability, or active physical edits; some failures require a restart.

The status header's ready boolean describes manager readiness, not an arena count. Per-template ready counts are the spare match slots. Preparation duration includes queueing, chunk work, and paste/verification; it is not isolated FAWE CPU time.

Instance States

StateMeaning
QUEUEDA region is reserved; preparation is waiting for budget.
PREPARINGChunk/paste/verification work is in progress. Not available to players.
READYThe generated arena is ready for a new match.
IN_USEA match owns the slot.
RESETTINGThe copy is being restored; a between-round reset can retain the same match ownership.
FAILEDQuarantined, not available. Diagnose before retrying.
RETIREDPermanently removed from rotation, but the region remains reserved.

These instance states are distinct from the regular /arena list arena lifecycle statuses. Use /arena instances commands for pool diagnostics.

Editing Templates and Gates

  • Edit the original arena, never the generated copy. Generated regions are reset from their accepted template revision.
  • Use /arena saveschem <original> after physical build changes. Metadata saves, completed schematic saves, gate changes/reloads, and config reloads also request coalesced source validation.
  • Active matches retain their accepted revision through their rounds. Eligible idle copies update first; busy copies adopt changes after their match releases them. Refresh does not rewrite a live fight.
  • Gate positions and eject points are translated with the copied arena. Follow Gate Setup on the original template.
  • A resized template must still fit its persisted reserved cell and the world's height limits. A restart does not automatically enlarge an existing cell; a different layout may need a new, unused instance-world name.
  • An invalid new source is not permission to publish an incomplete map. Inspect the refresh error; an existing accepted revision may remain in use.

Reloads, Upgrades, and Disabling

ChangeRequired action
Install a newer JARStop, back up, replace the JAR, and start. Missing config/message fields migrate additively. Existing explicit values are preserved; no config wipe is required.
Enable/disable instances, change world, selected templates, or spacingRestart. A config reload retains the active structural settings and logs a restart-required warning.
Change capacity/reserve/concurrency or auto-expand switch only/sd reload-config confirm. Lower caps stop growth; they do not delete existing or busy copies. The initial target is a startup target, not an immediate reload allocation request.
Turn the feature offSet arenas.instances.enabled: false and restart. Existing manual/legacy arena handling resumes. Instance-world files are left intact.

The instance migration adds the section in main config version 22 and operator messages in messages version 15. Let the plugin manage version fields; do not change them by hand to force or skip migrations.

Storage, Backups, and Safe Recovery

Back up the original arena data and schematics, plus the entire generated instance world with its hidden files. World storage may be a traditional world folder or a modern dimension directory, depending on the server. Keep the world's data and ownership metadata together.

  • .shyamduels-instance-owner identifies the owned world.
  • .shyamduels-instance-slots.properties records slot/template ownership and stable geometry.
  • Private frozen revisions keep busy matches on their accepted schematic. They are managed internally, not editable template files.
Do not remove safety metadata to force startup
A pre-existing unmarked folder is refused, even if empty. Ambiguous storage, changed identity, malformed manifests, and unsafe paths are also refused. Do not delete/edit ownership markers, manifests, lock files, or revision files to bypass an error. Stop and inspect the exact warning; restore a consistent backup or choose a genuinely new, unused destination name.

After a restart, persisted regions are re-prepared rather than trusted as ready. A timeout does not mean an underlying paste has physically stopped: wait for outstanding work before retrying, deleting, or attempting recovery.

/arena delete <generated-name> safely retires an eligible idle generated copy. Busy, queued, or physically editing copies are refused. Retirement does not erase world blocks or free/reassign that reservation; it remains counted toward capacity. Remove a selected original from templates and restart before deleting the source.

Sizing and Performance

  • Start with one selected template, two initial copies, and one concurrent preparation. Raise limits based on real preparation duration, MSPT, memory, and disk behaviour.
  • Preparations share arenas.reset-queue.max-concurrent with duel resets; normal resets have priority. Raising the instance concurrency setting alone cannot override that shared limit.
  • Keep selections tight around the playable region. Large air volumes, block entities, and saved entities still have parsing, paste, chunk, and memory costs.
  • The parsed-schematic cache has a 64 MiB accounting budget and 128-entry ceiling. This is not an exact JVM heap cap. Oversized resources are used transiently instead of retained, so repeated use may require additional parsing.
  • The implementation bounds work and coalesces demand; it does not make FAWE, world creation, or chunk loading free. Check a stopped Spark profile during a representative busy period before expanding production capacity.

Validation Limits, Not Capacity Recommendations

The loader accepts 1–4096 total slots, 1–1024 per-template maximum, 0–1024 initial/reserve values (each no greater than its template maximum), preparation concurrency 1–4, and spacing 16–4096 blocks. A template is limited to 1024 blocks per dimension and 16,777,216 cells, must fit world height and its reserved cell, and must pass schematic input checks. Source files are limited to 64 MiB; the expanded-input limit is 256 MiB, with additional structural limits. Validating below these limits does not guarantee that a particular server can run that capacity.

Troubleshooting Checklist

  1. Run /arena instances status <template>. Check that the manager is enabled and not paused, then distinguish ready, busy, queued, resetting, failed, and retired counts.
  2. Inspect a reported numeric slot with /arena instances slot <slot> and capture the last error plus relevant [ArenaInstances] log lines.
  3. Verify the template name, original DUEL type, corners, spawns, linked kit/build mode, saved schematic, capacity limits, and destination ownership.
  4. If growth is expected, verify both switches and minimum-ready. Queued/preparing/resetting supply and failed/retired reservations explain why another allocation may not occur.
  5. Correct the cause before retry or resume. Do not delete data or spam preparation commands while physical work remains active.

See also Troubleshooting: Instance Capacity, Configuration Files, and the command reference.
